## 一、十进制为什么优于二进制

计算器的用户想的是十进制。`0.1` 在二进制里是一个**无限循环小数**，
于是 `double` 只能把它近似成某个二进制数，`0.1 + 0.2` 的结果就是
`0.30000000000000004`。

这不是实现不够好，而是**表示与用户意图不匹配**。既然算的是十进制世界里的数，
内核就存十进制：

- 用户写 `0.1`，内核存的就是 `0.1`，不是「最接近 0.1 的 double」。
- 加减乘**完全精确**，因为十进制有限小数相加的结果仍然是有限小数。
- 需要近似的只有除法与超越函数，而这些运算**本来就**不精确 ——
  它们是唯一需要显式精度的运算。

代价是分块乘法比二进制慢（十进制分块 10⁹ 进制，二进制可以打包更多位）。
但本项目的场景是**十进制计算**，这个代价值得付。

## 二、数的表示：base-10⁹ 分块

内部表示是**小端**的 base-10⁹ 块序列：

```
值 = sign_ × Σ digits_[i] × 10^(9·i) × 10^(−scale_)
```

- `digits_[0]` 是**最低位**块。
- `scale_` 是小数位数（以 10 为单位）。
- 块是 `uint32_t`，因为 10⁹ < 2³²。

### 为什么是 10⁹ 而不是 10¹⁸

10¹⁸ < 2⁶⁴，所以 base-10¹⁸ 需要 `uint64_t` 块，乘法的中间结果
（两个 10¹⁸ 相乘 ≈ 10³⁶）**装不进 64 位**，必须做 128 位运算或拆分成两次乘法。
base-10⁹ 的乘法中间结果是 10¹⁸ < 2⁶⁴，**一个 `uint64_t` 就够**。

### 小端还是大端

小端（小块在前）有两个实际好处：

1. **除法天然适配**。长除法从最高位开始处理被除数，但每一步的余数操作
   （`remainder = remainder × 10⁹ + dividend[i]`）是**在低位追加** ——
   小端下就是「往末尾 push_back」，大端下要 insert 到开头（O(n) 搬移）。
2. **尾随零在 `digits_[0]`**，也就是「小数位那一侧」。

> ⚠️ **这个项目在实现时踩过这个坑。** 最初的 `normalize()` 在
> `digits_.back()`（最高位块）里找尾随零 —— 那找的是**整数部分**的零，
> 于是 `1.500` 归一化后还是 `1.500`。小端存储下，尾随零在 `digits_[0]`。
> 这个 bug 是被差分测试抓到的，不是被肉眼看出来的。

### 基准：为什么分块比单数字位快

单数字位（每个元素一位十进制数）的乘法是 O(n²)，分块也是 O(n²)，
但常数差约 **7 到 76 倍**（随位数放大）：

| 有效数字位 | 分块 (ms) | 单数字位 (ms) | 倍数 |
|---|---|---|---|
| 100 | 0.0018 / 0.0018 | 0.0178 / 0.0131 | 9.9× / 7.3× |
| 1000 | 0.0389 / 0.0317 | 1.8868 / 1.4232 | 48.5× / 44.9× |
| 10000 | 2.8255 / 2.0342 | 189.67 / 154.75 | 67.1× / 76.1× |

（左 = MSVC，右 = MinGW。）

差距随位数放大，因为分块把内层的「一位乘法 + 一次进位」变成了
「九位乘法 + 一次进位」，而外层的循环次数少了 9 倍。

**注意**：这个对比只计乘法本身，解析在计时之外。若把「十进制字符串 → 块」
的解析也算进分块版，分块版会**凭空多背一次 O(n) 解析**，而单数字位版
是直接构造数组 —— 那是**测量口径不一致**，不是算法差异。
（实测踩过：口径不一致时 100 位量出 0.73×，即「分块更慢」的假象。）

### base 必须是编译期常量

内层的取模与除法如果 base 是运行时参数，编译器就不能把它们折叠成常数乘法，
会退化成硬件除法。实测（4000 位 × 4000 位单数字位乘法）：

| | MSVC | MinGW |
|---|---|---|
| 运行时 base | 38.93 ms | 34.93 ms |
| 编译期常量 | 29.85 ms | 24.27 ms |
| 运行时更慢 | **+30.4%** | **+43.9%** |

所以核心把 base 固定成 10，**多进制只在表示层处理**（见 §15）。

## 三、字符串与块的互转

```cpp
Blk blocksFromDecimal(std::string_view text);   // 十进制串 → 小端块
std::string decimalFromBlocks(const Blk& blocks, int scale);
```

**切块**：从字符串末尾往前每次取 9 位，转成一个 `uint32_t`，`push_back`。
小端下从末尾开始切，恰好就是低位在前。

**还原**：块之间是 10⁹ 进制，所以**块边界天然对齐十进制位** ——
把最高位块转成十进制串（不补零），其余每块补足 9 位。

小数点位置由 `scale_` 单独记录，不参与块的计算。

## 四、精确四则

```cpp
BigDecimal operator+(const BigDecimal&) const;
BigDecimal operator-(const BigDecimal&) const;
BigDecimal operator*(const BigDecimal&) const;
```

**这三个不接受 `Context`** —— 它们完全精确，没有精度可言。
从编译期就杜绝了「精度被静默改变」这类错误。

加减法要先**对齐小数位**（见 §9），然后逐块加减并处理进位/借位。

## 五、归一化：尾随零的批量剥离

一个数的规范形式应该是没有多余尾随零的：`1.500` 规范化为 `1.5`，
`100` 规范化为 `1`（`scale_` 归零）。

### 这里有一个 120 倍的性能陷阱

尾随零可能成千上万 —— 高精度除法的商形如 `0.5000…0`（后面几千个零）。

**朴素写法**（逐个剥离）：

```cpp
while (scale_ > 0 && (digits_.size() > 1 || digits_[0] != 0)) {
    if (digits_[0] % 10 != 0) break;
    divideBy10(digits_);      // ← 每次都要遍历整个数组
    --scale_;
}
```

每次 `divideBy10` 都是 O(块数)，剥掉 n 个零就是 **O(n × 块数)** ——
而块数本身正比于总位数，所以总复杂度是**二次方**。

**批量写法**（本项目采用）：

```cpp
while (scale_ > 0 && (digits_.size() > 1 || digits_[0] != 0)) {
    // 整块剥离：最低位块为 0，说明它 9 个十进制位全为零。
    std::size_t zeroBlocks = 0;
    while (zeroBlocks + 1 < digits_.size() && digits_[zeroBlocks] == 0) ++zeroBlocks;
    const std::size_t affordable = static_cast<std::size_t>(scale_ / kBlockDigits);
    const std::size_t strip = zeroBlocks < affordable ? zeroBlocks : affordable;
    if (strip > 0) {
        // 一次性 erase，避免重复搬移
        digits_.erase(digits_.begin(), digits_.begin() + static_cast<std::ptrdiff_t>(strip));
        scale_ -= static_cast<int>(strip) * kBlockDigits;
        continue;
    }
    // 块内零：最低位块非零，但它的末尾可能有零（最多 8 个）。
    int zeros = 0;
    std::uint32_t probe = digits_[0];
    while (probe % 10 == 0 && zeros < kBlockDigits) { ++zeros; probe /= 10; }
    if (zeros == 0) break;
    const int removed = zeros < scale_ ? zeros : scale_;
    for (int i = 0; i < removed; ++i) divideBy10(digits_);
    scale_ -= removed;
    break;
}
```

先**数出**能剥多少块，再**一次性** `erase` —— 避免反复搬移。
块内不足 9 个零时才逐个处理。

**实测**：precision = 1000000 的除法，从 **24,110 ms 降到 201 ms（约 120×）**。
这一个函数是整个项目里单点收益最大的优化。

## 六、长除法：逐块 + 二分试商

```cpp
std::pair<Blk, Blk> BigDecimal::divideBlk(const Blk& dividend, const Blk& divisor);
```

商与余数一起算出来。算法是教科书上的逐块长除法：

```
for 每个被除数块 i（从最高位到最低位）:
    remainder = remainder × 10⁹ + dividend[i]
    digit = 最大的 q 使得 divisor × q ≤ remainder     ← 二分试商
    remainder -= divisor × digit
    quotient.push_back(digit)
```

### 二分试商

商的一个块在 `[0, 10⁹)`，所以二分需要约 30 次比较。
每次比较是一次**单块乘法**（O(块数)），所以试商总共 O(30 × 块数)。

> **为什么不直接除？** 因为 `divisor × q` 需要多块表示，二分试商用
> `mulBlk(divisor, {mid})` 做乘法 —— 单块乘法比通用除法简单得多。

### 两个容易写错的地方

1. **进位必须 `push_back`**（追加到最高位）。小端表示的末尾是最高位。
   写成 `insert(begin(), ...)` 会把进位放到最低位，结果完全错乱。
2. **商在累积时是最高位在前**，最后必须 `reverse` 成小端。

这两点原型阶段各栽过一次，都是被差分测试抓出来的。

### 为什么不用 Knuth Algorithm D

Knuth D（归一化 + 试商估计 + 加回修正）常数因子更小，但它：

- 需要**预估**试商，且预估必须带修正逻辑 —— 代码量大、边界多；
- 本项目的除法结果还要走**精确余数判定**（§7），而 D 的中间量
  （`q̂` 与 `r`）与这个判定耦合得很别扭。

**当前实现的取舍**：可审计、易验证、正确性有 484 个差分用例背书。
性能不是瓶颈 —— 除法在 1600 位精度下只要 2.4 ms（见 §16），
而真实使用场景很少超过几百位。

Knuth D 是一条**后续方向**（§17），不是当前实现的一部分 ——
所以本文**不给出**它的任何性能数字。

## 七、舍入：为什么必须用精确余数

这是整个内核最关键的一处设计。

### 错误的做法：「多算几位再猜」

一种常见做法是：多算几位（比如多算 2 位保护位），然后看被丢弃的那几位
「是不是 5」来决定进位。

**问题在于没有 sticky bit。**

考虑 `0.4999999…` 在 1 位小数上舍入。被丢弃的部分是 `4999999…`，
它的**第一位是 4**，看起来「小于一半」→ 不进位。但正确答案是**进位**，
因为 `0.4999999…` 实际上就是 `0.5`。

判断「被丢弃部分是否 ≥ 0.5」需要知道**整个**被丢弃部分的信息 ——
而「多算几位」只看前几位，丢掉了更后面的信息。

同样地，`0.5000001` 的第一位是 `5`，看起来「正好一半」→
按银行家舍入应该看「恰好一半」这个**精确**条件，但实际它比一半大，
应该进位。

### 正确的做法：精确余数

本项目的做法是**把被丢弃部分精确地算出来**：

```cpp
// 精确分数 N/D 舍入到 p 位有效数字。
// 用**长除法得到的精确余数**判断被丢弃部分与半个 ulp 的关系，
// 而不是"多算几位再猜"。因此「正好一半」（银行家舍入要走偶数分支）
// 与「超过一半」永远能被正确区分。
std::pair<Blk, int> BigDecimal::roundQuotient(const Blk& numerator, const Blk& denominator,
                                               int precision, RoundingMode mode, bool negative);
```

长除法天然给出**精确余数**（§6）。余数与除数的关系就是
「被丢弃部分与半个 ulp 的关系」的**精确**判据：

- 余数 × 2 < 除数 → 严格小于一半
- 余数 × 2 = 除数 → **正好一半**（`HalfEven` 走偶数分支）
- 余数 × 2 > 除数 → 严格大于一半

没有舍入误差，没有 sticky bit 问题，没有双重舍入。

**这是差分测试证明「别的做法是错的」的地方**：`verify_div.py` 的参考实现
用 `fractions.Fraction` 做**精确有理数**运算再手工按指定模式舍入 ——
它与 C++ 端**没有任何共享代码**，所以两者一致才是真正的证据。

## 八、舍入模式语义表

| 模式 | 名称 | 语义 |
|---|---|---|
| `HalfEven` | 四舍六入五成双 | 正好一半时取偶数（银行家舍入）|
| `HalfUp` | 四舍五入 | 正好一半时进位 |
| `Down` | 向零截断 | 总是截断 |
| `Up` | 远离零截断 | 总是进位 |
| `Ceil` | 向 +∞ 取整 | 正数进位、负数截断 |
| `Floor` | 向 −∞ 取整 | 正数截断、负数进位 |

「正好一半」由**精确余数**判定（§7），不是由「多算几位再猜」判定 ——
这正是 `HalfEven` 与 `HalfUp` 唯一会分歧的地方。

`Ceil` 与 `Floor` 的方向与符号相关，这一条有专门的差分用例覆盖
（`divide.rounding_direction_on_negatives`）。

## 九、对齐小数位：一个被低估的二次方陷阱

加减法要求两个数的 `scale_` 相同。做法是给 `scale_` 小的那个**末尾补零**。

**朴素写法**：`mulBlk(digits, 10^delta)` —— 一次通用的大数乘法，O(块数²)，
而且每次都要先把 `"1" + delta 个 '0'` 拼成字符串再解析成块。

**正确写法**：补零就是「乘以 10^delta」，而 10 的整数次幂在十进制下
就是**移小数点** —— 直接移块，**O(块数)**：

```cpp
int BigDecimal::alignScale(BigDecimal& lhs, BigDecimal& rhs) {
    if (lhs.scale_ == rhs.scale_) return lhs.scale_;
    if (lhs.scale_ < rhs.scale_) {
        const int delta = rhs.scale_ - lhs.scale_;
        lhs.digits_ = shiftLeftDecimal(std::move(lhs.digits_), delta);
        lhs.scale_ += delta;
    } else {
        const int delta = lhs.scale_ - rhs.scale_;
        rhs.digits_ = shiftLeftDecimal(std::move(rhs.digits_), delta);
        rhs.scale_ += delta;
    }
    return lhs.scale_;
}
```

### 为什么这一处特别重要

超越函数的级数**每一项都要做加法与比较**，也就是**每一项都要 alignScale 两次**。
于是这个二次方开销把整个级数拖回**三次方**。

这不是理论推断 —— 优化前超越函数确实是三次方，而优化后降到接近平方级
（§11、§16）。`alignScale` 的线性化是其中一块关键拼图。

## 十、开方：牛顿迭代

```
x ← (x + n/x) / 2
```

牛顿法对平方根是**二次收敛**的 —— 每迭代一次有效位翻倍。

### 初值必须来自 n 的真实量级

```cpp
const int e = value.decimalExponent();
const int h = floorHalf(e);           // floor(e/2)
const BigDecimal scaled = shiftByPowerOfTen(value, -2 * h);
BigDecimal guess(1);
```

把 n 分解成 `m × 10^(2h)`，其中 `m ∈ [1, 100)`，真根落在 `[1, 10)`。
移位是**精确**的位操作，不引入任何舍入。初值取 1，与真根同量级，
牛顿法收敛良好。

> ⚠️ **踩过的坑**：最初的实现把 n 放大 `10^(2·guard)` 后用字符串的位数推初值 ——
> 放大后 `scale_ = 2·guard`，字符串里整数部分的位数**与 n 的量级无关**，
> 于是 `value = 2` 会得到初值 1（真实答案是 `1.414e(guard)`），
> 而迭代上界只有 `guard + 10` 步，**收敛不住**。
> 现在从 `decimalExponent()` 拿真实量级。

### 收敛判据

```cpp
const BigDecimal epsilon = shiftByPowerOfTen(BigDecimal(1), -(work.precision - 1));
// 相邻两次迭代之差 ≤ epsilon 就停
```

真根在 `[1, 10)`，工作精度下 1 ulp 是 `10^-work.precision`；
判据放宽到 10 ulp，兼顾「舍入导致在两个相邻值间摆动」。

`(guess + quotient) / 2` 用**精确的除以二**（`divideByTwo`），
避免多一次舍入。

## 十一、exp：泰勒级数与范围缩减

### 泰勒级数

```
exp(g) = 1 + g + g²/2! + g³/3! + ...
```

调用方保证 `0 ≤ g < ln(10) ≈ 2.303`，**项全部为正** —— 没有抵消，数值稳定。
需要的项数约 `1.4 × precision`。

每一项都要**限制在工作精度内**（`roundToPrecision`），
否则 `term` 的小数位会随迭代增长。

### 范围缩减

```
exp(x) = 10^k × exp(g),   g = x − k·ln(10),  k = floor(x / ln(10))
```

`g ∈ [0, ln(10))`，于是级数的收敛性与参数大小无关。

### 工作精度按「真正被抵消掉多少」决定 —— 这是本节最要紧的一点

`g = x − k·ln(10)` 里被抵消掉的量级是 `|k·ln(10)| ≈ |k|`。
所以「要保护几位」由 **`|k|` 决定，与 x 的量级无关**。

**按 `|x|` 的十进制指数给保护位是错的**：x 极小时（`1e-200`）`k = 0`，
根本没有抵消，一位保护位都不需要；而那个公式会多算 205 位。

| 参数 | 精度 | 耗时 (MSVC) | 耗时 (MinGW) |
|---|---|---|---|
| `exp(1e-200)` | 30 | 0.24 ms | 0.21 ms |

而 `exp(1e-99000)` 在错误公式下是**永远算不完**（源码注释记录：45 秒起）。

### `|x| < 1` 时完全绕开除法

```cpp
const bool tinyArgument = magnitude < 0;
if (tinyArgument) {
    k = value.sign_ < 0 ? BigDecimal(-1) : BigDecimal(0);
}
```

- `x ≥ 0` → `x/ln(10) ∈ [0, 0.435)` → `k = 0`
- `x < 0` → `x/ln(10) ∈ (−0.435, 0)` → `k = −1`

绕开除法不是可有可无的优化：除法要先对齐小数位，而长除法是 O(位数²) ——
x 的小数位有 99000 个时，实测 `exp(1e-99000)` 要 45 秒。

走这条支与走除法的结果**完全一致**：除法得到的商四舍五入后仍在
`(−0.435, 0.435)` 内，`floor` 必然是同一个整数，`g` 也逐位相同。

### 大参数的保护位

`|x| ≥ 1` 时 `k` 要靠除法得到。先用 **20 位探针**估 `|k|` 的**量级**
（探针只用来量级，不参与最终计算）：`|x| < 10⁵` 时 `|k| < 43427`，
所以 20 位探针足够把量级定死。然后保护位数 = `|k|` 的十进制位数 + 5。

## 十二、ln：atanh 级数

用 `atanh` 而不是直接用 `ln` 的泰勒级数：

```
ln(x) = 2·atanh(z),   z = (x−1)/(x+1)
```

`atanh(z) = z + z³/3 + z⁵/5 + …` —— 只含**奇次幂**，收敛快得多。

### 两条路径

```cpp
// 路径 1：靠近 1 的直接展开。
if (value.compare(half) >= 0 && value.compare(two) <= 0) {
    const BigDecimal z = divide(value - one, value + one, ...);
    return multiplyByTwo(atanhSeries(z, work));
}
// 路径 2：量级分解。
```

`x ∈ [0.5, 2]` 时 `|z| ≤ 1/3`，直接展开。
否则分解成 `x = m × 2^h × 10^e`（`m ∈ [1, 2)`），用
`ln(x) = h·ln(2) + e·ln(10) + ln(m)`。

**注意**：路径 1 里 `z = (x−1)/(x+1)`，x = 1 时 `z = 0`，级数立刻收敛 ——
这正是 `ln(1)` 有一条「早退路径」的原因（见 §16 的测量陷阱）。

### ln(2) 与 ln(10) 按精度实时计算

```cpp
BigDecimal BigDecimal::ln2Constant(const Context& work) {
    const BigDecimal z = divide(BigDecimal(1), BigDecimal(3), ...);
    return multiplyByTwo(atanhSeries(z, work));
}
BigDecimal BigDecimal::ln10Constant(const BigDecimal& ln2, const Context& work) {
    const BigDecimal z = divide(BigDecimal(1), BigDecimal(9), ...);
    const BigDecimal lnOneAndAQuarter = multiplyByTwo(atanhSeries(z, work));
    return ln2 * BigDecimal(3) + lnOneAndAQuarter;
}
```

`ln(2) = 2·atanh(1/3)`，`ln(10) = 3·ln(2) + ln(5/4)`，而 `ln(5/4) = 2·atanh(1/9)`。

**不用硬编码常量**：硬编码的 60 位常量在 `precision > 60` 时不够用，
而高精度计算器正是本项目的存在意义。

`ln(10)` 接受 `ln2` 作为参数 —— 一次 ln 运算里 `ln(2)` 会被用到好几处，
重算一遍 atanh 级数的代价不小。

### 级数里必须限制工作精度

```cpp
// **每一项都要限制在工作精度内**，否则小数位会无限增长：
// z 的小数位约为 work.precision，而 z*z 的小数位是它的两倍，
// 第 k 次迭代的 power 小数位达到 (2k+1) * work.precision。
```

不限制的话，`work.precision = 110`、`k = 230` 时中间数会有 5 万位十进制数 ——
除法的开销随之从毫秒级涨到几十秒。

舍入到工作精度是安全的：级数的项**单调递减**，每一项的**相对**精度才是关键，
截掉的是远低于 ulp 的低位。

### 除以小整数走线性路径

```cpp
const BigDecimal addend = divideBySmallInt(power, static_cast<std::uint64_t>(2 * k + 1),
                                           Context{work.precision, RoundingMode::HalfEven});
```

语义与 `divide(power, BigDecimal(2*k+1), ...)` **完全一致**，
但除法从 O(块数²) 降到 O(块数) —— 这一项是级数里的**主项**。

## 十三、log10 与整数次幂

`log10` 与 `ln` 同样的两条路径，但拆成「指数部分 + 尾数部分」，
这样 **10 的整数次幂给出精确的整数**（`log10(1000) = 3`，不是 `2.999…`）。

`pow` 分两条路：

- **整数次幂** → 走**精确的快速幂**（`integerPower`），不受
  `kMaxTranscendentalPrecision` 限制，只受 `kMaxIntegerPower`（指数）
  与 `kMaxPowerResultDigits`（结果位数）限制。
- **非整数次幂** → `exp(exponent × ln(base))`，受超越函数精度上限约束。

这个区分很重要：一个 `pow(2, 10000)` 是**精确**的（一个整数），
不该被「超越函数只能算 1000 位」的规矩卡住。

## 十四、精度与误差传播

### 误差只在一处产生

加减乘全程精确。除法与超越函数的**最后舍入**是唯一的误差来源。

### 工作精度

```cpp
constexpr int kGuardDigits = 10;        // 保护位
constexpr int kMinWorkPrecision = 24;    // 工作精度的下限
```

超越函数在工作精度下计算（用户精度 + 10 位保护位），
最后才舍入到用户精度。保护位吸收了中间计算的舍入误差。

### 运算上限是公开契约

```cpp
kMaxPrecision                = 100000   // 除法与舍入
kMaxTranscendentalPrecision  = 1000     // 超越函数
kMaxIntegerPower             = 100000   // pow 的整数次幂
kMaxPowerResultDigits        = 300000   // pow 的结果位数
kMaxExponentMagnitude        = 1000000  // 科学计数法的指数
```

超越函数的上限定在 1000 是**产品决策**，不是数学限制 ——
它们的代价是平方级的（见 §16），`precision = 1600` 时最坏情况要两分半。
真正需要更高精度的调用方应该分批求值。

### 精度越界被拒绝，不静默夹取

```cpp
if (context.precision > kMaxPrecision) {
    throw std::invalid_argument(...);
}
```

用户要的是他请求的那个精度，悄悄换个精度等于给出一个他没要求的答案。

## 十五、多进制与位运算

### 进制是表示层的问题

核心**始终是 base-10**。进制转换是反复除法 + 乘法，
整数部分**精确无损**。

小数部分在该进制下无法有限表示时（如 `1/3` 在三进制下），
按目标进制逐位提取，**显式标注截断**（末尾的 `...`），**不做无声的近似**。

`toBaseString` 的「...」契约：

- "..." 表示「展开**被截断了**」，且截断的是**小数部分**；
- 出现 "..." 时，前面的数字是展开的**真实前缀**（不是四舍五入的近似值），
  末位数字也是真实数字 —— 删掉它会改变数值；
- 该进制下**能**有限表示的值**通常**不带 "..."；但如果展开长度太大、
  超出工作量上限，它同样会带 "..." —— 那时它确实没写完。

**工作量上限**：展开代价是 O(位数 × 块数)。预算大到算不完时，
`toBaseString` **不会**抛异常 —— 它算出算得动的那部分位，**截断**并
如实加上 "..."。理由：计算器的调用方要的是一个答案（哪怕带标记的近似值），
而不是一个空洞的异常；「...」的含义本来就是「没算完」，
如实标记不算撒谎 —— **撒谎的是「算完了却说没算完」**，那是相反的方向。

### 反向解析只接受整数

`fromBaseString` **只接受整数**：任意进制的小数未必能在十进制内核里
精确表示（`1/3` 在三进制下无法有限表示），接受它就等于引入无声的近似。
输出侧用 "..." 标记截断，解析侧则直接拒绝。

### 位运算仅对整数精确

`&` `|` `^` `~` `<<` `>>` 通过二进制表示实现，**仅对整数**精确支持。
浮点位运算一律拒绝并给出明确错误。

负数采用**无限位二进制补码**语义（与 Python 的 `int` 一致）：
`-1 & x == x`、`-1 | x == -1`。右移**向 −∞ 取整**（`-1 >> 100 == -1`）。

### 关于「从三次方降到接近平方级」

精度翻倍时耗时约 **2.6×**（MSVC exp：1.46 → 3.82 → 11.83 → 53.74）。
平方级应该是 4×。所以准确措辞是「**接近平方级、略高于平方**」——
不是「平方级」，更不是「线性」。

### 三条测量口径（每条都对应一个会骗人的坑）

1. **只计运算本身**，解析在计时之外。口径不一致会让 100 位乘法量出
   0.73× 这种「分块更慢」的假象。
2. **重复多次取最小值**，不要单次计时也不要取平均。最小值最接近算法
   本身的代价。
3. **base 必须真正不可知**（取自 `volatile`），否则编译器把 `%` 与 `/`
   折叠成常数，两版完全一样，量出「运行时 base 没有代价」的**假绿**。

还有一条**选输入**的坑：量 `ln` 时**不能用 `ln(1)`** ——
它有一条早退路径，会量出 0.0003 ms 的假象（真实的级数代价是 0.2 ms 起）。
本文用 `ln(2)`。

## 十七、已知的后续方向

这些是**没有实现**的方向，本文因此**不给出任何性能数字**：

- **Knuth Algorithm D**：归一化 + 试商估计 + 加回修正。当前用「逐块 +
  二分试商」，可审计性优先；当位数上到十万级时，D 的常数因子优势才会显现。
- **快速乘法**（Karatsuba / Toom-Cook）：当前乘法是 O(n²)。
- **牛顿迭代的高精度加速**（用高精度乘除法做双精度牛顿步，再做修正），
  可以把超越函数的复杂度再降一档。
